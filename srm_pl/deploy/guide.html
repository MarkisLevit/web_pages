How it fits together

Before typing anything, it helps to know what you're building. When someone types your domain into a browser, four separate things have to cooperate. Most deployment problems are really just one of these four being misconfigured — so if you can name them, you can debug them.

01

DNS

The internet's address book. Turns yourdomain.pl into an IP number.

02

The VPS

A computer in a data centre that is always on. Yours, rented from Hostinger.

03

Caddy

The web server. Listens for visitors, hands back files, handles the HTTPS padlock.

04

Your files

The HTML, CSS, images — plus one PHP file that sends the contact form.

So the journey is: visitor asks DNS “where is this domain?” → DNS answers with your VPS's IP → the browser knocks on that VPS → Caddy answers, proves its identity with a certificate, and sends back your files.

Why we're using Caddy

You may have seen guides using Apache or nginx. Those work, but they need a separate tool (certbot) to get an HTTPS certificate, plus a scheduled job to renew it every 90 days. Forget that job and your site starts showing scary browser warnings.

Caddy gets and renews certificates by itself, with no extra setup. For a site that a small team maintains, that's one fewer thing that can quietly break a year from now.

Step 1

Prepare the VPS

~5 min

Log in to Hostinger and open hPanel. In the top menu choose VPS, then click Manage on your server. You're looking for two things here.

a. Check which operating system is installed

Find the OS & Panel section. It must say Ubuntu (22.04 or 24.04) with no control panel — no cPanel, no CyberPanel, no Plesk.

This one matters

Control panels install their own web server, which permanently occupies ports 80 and 443 — the two doors Caddy needs. If a panel is installed, Caddy will refuse to start and the error message won't obviously say why.

If you see a panel listed, reinstall the OS now: OS & Panel → Change OS → Ubuntu 24.04 (plain). This wipes the server, so do it before you put anything on it.

b. Write down your IP address and root password

The Overview page shows your server's IP address — four numbers like 203.0.113.45. That's the street address of your computer in the data centre. Copy it somewhere; you'll use it constantly.

Under SSH Access you'll find the root password. “Root” is the Linux equivalent of Administrator — an account that can change anything. If you never set a password, use that panel to set one now.

Before moving on
You have: the IP address, the root password, and confirmation that the OS is plain Ubuntu.
Step 2

Connect with SSH

~5 min

Your VPS has no screen and no mouse. You control it by typing commands over an encrypted connection called SSH. Think of it as a secure phone line to the server's command prompt: what you type goes there, what it prints comes back.

On Windows, use Git Bash (installed with Git for Windows). Open it from the Start menu. Everything in this guide assumes Git Bash, not PowerShell or CMD.

Your PC Git Bash replace with your real IP
ssh root@203.0.113.45

The very first time, you'll see something like this:

The server First connection
The authenticity of host '203.0.113.45' can't be established.
ED25519 key fingerprint is SHA256:qLm8w...
Are you sure you want to continue connecting (yes/no)?

Type yes and press Enter. Your computer is saying “I've never met this server, I have no way to know it's really yours.” After you accept, it remembers the server's fingerprint and will warn you if it ever changes. Then enter the root password — nothing appears as you type, not even dots. That's normal; just type it and press Enter.

When the prompt changes to something like root@srv123:~#, you are on the server.

Optional but recommended: log in without a password

Typing the password every time gets old, and passwords can be brute-forced. An SSH key is a pair of files: a private one that stays on your PC and a public one you give the server. Only the matching pair opens the door.

Your PC Create the key press Enter at every prompt
ssh-keygen -t ed25519 -C "srm-deploy"
Your PC Send the public half to the server
cat ~/.ssh/id_ed25519.pub | ssh root@203.0.113.45 \
  "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
Check it worked
Type exit to leave, then ssh root@203.0.113.45 again. It should let you straight in with no password.
Step 3

Point your domain at the server

~5 min + waiting

Right now your domain points nowhere useful. You need to create an A record — a single line in the internet's address book that says “this name lives at this IP”.

If your domain is registered with Hostinger: hPanel → Domains → click your domain → DNS / Nameservers → DNS Zone. Delete any existing A records for @ and www, then add these two:

TypeNamePoints toTTL
A@203.0.113.453600
Awww203.0.113.453600

@ means the bare domain (yourdomain.pl) and www means the www version. TTL is how many seconds other computers are allowed to cache the answer — 3600 is one hour.

If it's registered elsewhere (OVH, GoDaddy, Namecheap), add exactly the same two records in that provider's DNS panel instead.

Now wait, and verify

DNS changes spread across the world gradually — usually 5–30 minutes. Check with this, which asks Cloudflare's public DNS server directly:

Your PC Git Bash
nslookup yourdomain.pl 1.1.1.1

Keep running it until the answer contains your VPS IP.

Don't skip ahead

Wait for DNS before running the setup script. Caddy asks Let's Encrypt for a certificate the moment it starts, and Let's Encrypt proves you own the domain by visiting it. If DNS isn't ready, that check fails.

Fail it too many times in an hour and Let's Encrypt rate-limits you for several hours — you'd simply have to wait it out. Patience here saves an afternoon.

Step 4

Get an email password ready

~5 min

The setup script in the next step will ask for email credentials, so get them first — it's annoying to be interrupted halfway through.

The contact form needs to actually send email. You might expect the server to just send it directly, and technically Linux can. In practice it doesn't work:

  • Hostinger blocks port 25, the port used for direct mail delivery. Nearly every VPS provider does, because spammers abuse cheap servers.
  • Nobody trusts a new IP. Gmail and Outlook check whether a sending server has a reputation and proper DNS records. A fresh VPS has neither, so mail lands in spam or is rejected.

So instead we relay: the server logs into a real email provider and asks it to send on our behalf. The provider already has the reputation. The quickest option is a Gmail App Password.

Creating a Gmail App Password

  1. The Google account must have 2-Step Verification switched on. If it doesn't, turn it on first — app passwords aren't offered otherwise.
  2. Go to myaccount.google.com/apppasswords.
  3. Create one named srm-website.
  4. Google shows a 16-character code. Copy it now — it's never shown again.
What an app password is

It's a single-purpose password that only works for sending mail, and can be revoked on its own. Your real Google password keeps protecting your actual account — so if the server were ever compromised, the attacker gets the ability to send email, not your inbox.

Have these four things ready:

Hostsmtp.gmail.com
Port587
Usernameyour full Gmail address
Passwordthe 16-character app password (not your normal one)
Use the same address for “from”
When the script asks for the FROM address, give the same Gmail address you authenticated with. Gmail rewrites the sender if they don't match, which breaks delivery.
Step 5

Set up the server

~5 min

Now you install everything the site needs. Two files do this: server-setup.sh (the installer) and Caddyfile (the web server's configuration). First copy them up with scp — “secure copy”, SSH's file-transfer twin.

Your PC From the project folder
# move into the project folder first
cd /m/Work/web_pages/srm_pl

scp deploy/server-setup.sh deploy/Caddyfile root@203.0.113.45:/root/

The :/root/ at the end is the destination on the server. Everything before the colon is local; everything after is remote.

Now run it:

Your PC Runs remotely over SSH
ssh root@203.0.113.45 "bash /root/server-setup.sh"

It will ask you, in order:

  1. Your domain — without www and without https://. Just yourdomain.pl.
  2. An email address — Let's Encrypt uses it to warn you if a certificate ever fails to renew.
  3. SMTP details — the four things from Step 4. The password won't appear as you type it.
  4. Deliver-to address — where contact form messages should arrive.

What it's installing, and why

PieceWhat it's for
CaddyThe web server. Serves your files and manages HTTPS certificates automatically.
PHP-FPMRuns the one PHP file that sends the contact form. Configured to run only that folder.
ufwA firewall. Opens ports 22 (SSH), 80 and 443 (web); everything else stays shut.
/etc/srm/smtp.confYour email password, stored outside the website folder so it can never be served to a visitor by accident.
A note on security

PHP is the only part of this site that executes code, so it's the only part an attacker could target. The setup deliberately fences it in: it can read just three folders, and the commands that run other programs (exec, shell_exec, system) are switched off entirely.

Check it worked
The script finishes by printing a summary with your domain, the site folder and the PHP socket. If it stopped with a red [!] message instead, fix what it names and run it again — re-running is safe.
Step 6

Set the domain in the site files

~1 min

The website was built with a placeholder domain baked in. It appears in 105 places — canonical tags, the Polish/English language links, social sharing previews, the sitemap and the JSON-LD that Google reads.

These aren't cosmetic. Get them wrong and Google may index the wrong address, and links shared on Facebook can show a broken preview. One command fixes all of them:

Your PC In the project folder
bash deploy/set-domain.sh yourdomain.pl

It prints each file it changed and how many references it replaced, then confirms that none of the old domain is left behind.

Check it worked
The last line should read Remaining references to the old domain: 0.
Step 7

Upload the website

~2 min

Tell the deploy script where your server lives. Copy the example config and edit it:

Your PC Create your config
cp deploy/deploy.conf.example deploy/deploy.conf
notepad deploy/deploy.conf

Set VPS_HOST to your IP address, save, close.

Why this file is separate

deploy.conf is listed in .gitignore, so your server address never gets committed into the repository. The example file is committed; your real one stays on your machine.

Always do a dry run first. It shows exactly what would change without touching anything:

Git Bash, not PowerShell

In PowerShell, bash is the WSL launcher, not Git Bash — the script fails with execvpe(/bin/bash) failed before it starts. Run the commands below in Git Bash, or use the PowerShell wrapper .\deploy\deploy.ps1 --dry-run, which finds Git Bash for you.

Your PC Preview
bash deploy/deploy.sh --dry-run

If the list looks right, do it for real:

Your PC Deploy
bash deploy/deploy.sh

The script uploads the files, sets the correct owner and permissions, then reloads Caddy.

What --delete means
The upload makes the server mirror your folder exactly. Files you deleted locally get deleted on the server too. That's what you want for a website — but it also means anything you edited directly on the server, and not locally, will be wiped. Always edit locally and deploy.
Step 8

Verify it works

~5 min

a. Open the site

Visit https://yourdomain.pl. The very first load may take a few seconds — that's Caddy fetching your certificate from Let's Encrypt while you wait. You should see the padlock in the address bar.

Watch it happen live if you're curious:

Your PC Live log — press Ctrl+C to stop
ssh root@203.0.113.45 "journalctl -u caddy -f"

b. Click through everything

  • Both languages — the PL / EN switch in the header
  • Every menu item in both languages
  • A donation button (it should open GiveLively in a new tab)
  • A made-up address like yourdomain.pl/nothing — you should get the branded 404 page
  • An old Tilda link like yourdomain.pl/kids — it should redirect to the programmes page

c. Test the contact form

Fill it in and submit. You should land on the thank-you page and get an email within a minute. Reply to that email — it should go back to whoever filled in the form, not to yourself.

If it fails, the reason is in the log. This is the single most useful command here:

Your PC Read the form's error log
ssh root@203.0.113.45 "journalctl -u php8.3-fpm -n 50 | grep srm-contact"

Every failure is logged with what the mail server actually replied, so you see the real cause rather than guessing. If php8.3-fpm isn't found, check the version with systemctl list-units 'php*fpm*'.

You're live when
The padlock shows, both languages load, www redirects to the bare domain, and a test message reaches your inbox.
Step 9

Keep it running

~10 min once

Automatic security updates

A server nobody updates slowly becomes a liability. Ubuntu can install security patches by itself:

The server Run once
apt install -y unattended-upgrades
dpkg-reconfigure --priority=low unattended-upgrades

Backups

In hPanel under VPS → Snapshots & Backups you can take a snapshot — a full image of the server you can restore to. Take one now, while everything works. It costs nothing and it's the difference between a bad ten minutes and a bad weekend.

Your website content is already safe: it lives in Git on your PC. The snapshot is for the server's own configuration.

Publishing changes later

Edit files locally, check them, then run one command:

Your PC Every future update
bash deploy/deploy.sh

Changing the email settings

If the app password is ever revoked, or you switch to a provider like Brevo or Resend:

The server Edit and save
nano /etc/srm/smtp.conf

Save with Ctrl+O then Enter, exit with Ctrl+X. No restart needed — the form reads the file fresh on every submission.

Reference

When something goes wrong

Work down this table — the causes are ordered roughly by how often they're the real problem.

SymptomCause and fix
Browser can't reach the site at all DNS hasn't propagated yet. nslookup yourdomain.pl 1.1.1.1 must return your VPS IP. If it returns something else, the A record is wrong.
Certificate warning, or stuck on plain HTTP Caddy couldn't complete the Let's Encrypt check. Port 80 must be reachable from the internet — check the hPanel firewall, then read journalctl -u caddy -n 50.
Caddy won't start at all Something else is holding ports 80/443, almost always a control panel's web server. Run systemctl disable --now apache2 nginx, then systemctl restart caddy.
permission denied opening a log file Caddy treats a log it cannot open as a fatal config error and exits rather than starting without it — so a logging problem takes the whole site down. Don't chase the permission; remove the file log. Replace the log block in /etc/caddy/Caddyfile with output stderr and read logs via journalctl -u caddy instead. Current copies of the Caddyfile already do this.
Deploy says “Unit cannot be reloaded because it is inactive” Not a deploy problem — Caddy is already dead from an earlier error. Your files uploaded fine. Run journalctl -u caddy -n 30, fix what it names, systemctl restart caddy.
execvpe(/bin/bash) failed, or a wsl.conf warning You ran the script from PowerShell, where bash means C:\Windows\System32\bash.exe — the WSL launcher, not Git Bash. If WSL is missing or broken it fails before the script even starts. Either open Git Bash and run it there, or from PowerShell use the wrapper: .\deploy\deploy.ps1 --dry-run.
Permission denied (publickey,password) SSH reached the server but couldn't authenticate. You have no SSH key, so it wants the root password — and a non-interactive shell can't supply one. Set up a key once (Step 2) and the deploy runs without prompting.
Contact form shows a 502 error PHP isn't running or Caddy can't reach it. Check systemctl status php8.3-fpm and confirm /run/php/php-srm.sock exists.
Form says “could not send” The mail server rejected the login. Nine times out of ten it's a normal Gmail password used instead of an app password. Read the log line from Step 8c.
Form hangs, then fails Outbound SMTP may be blocked. Test with nc -zv smtp.gmail.com 587 on the server. If it hangs, open a Hostinger support ticket asking to unblock outbound SMTP.
Changes don't appear after deploying Your browser cached the old page. Hard-refresh with Ctrl+Shift+R.
Polish characters look like ÅÄ The file was saved as Windows-1250 instead of UTF-8. Re-save it as UTF-8 in your editor and deploy again.
